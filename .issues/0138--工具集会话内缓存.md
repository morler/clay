## 2026-11-18 核实：验收已满足，不加缓存层

**验收「同一会话两次请求 tools JSON 逐字节一致」：已满足，并已加断言。**

`clay_commands_tools_build` 是纯函数：整段构建代码里 `commands->` 出现 0 次，没有哈希容器（无迭代顺序不稳定），唯一的副作用是首次调用时的 MCP 连接，而它由 `mcp_connect_attempted` 保证只发生一次。

新增断言（`tests/test_token_budget.c`）：同一会话连续两次构建 + `clay_commands_reset_conversation` 之后再次构建，三者**逐字节相同**（8245 B）。

反证：让 `task_list` 的描述带上构建计数器 `(build N)`，断言立即失败（`strcmp(first_build.data, second_build.data) == 0`）。

**为什么不实现「会话内复用」**：实测重建成本 **16.81 µs**（20000 次连续构建 336 ms）。

- 典型 20 轮 turn：0.34 ms，占 LLM 单轮延迟（秒级）的 0.01%
- 最坏 64 轮上限：1.08 ms

而缓存层需要处理的是：模型/provider 切换时失效、subagent 各自持有不同 `plan` 时不能共享、MCP 状态变化时重建、多线程并发访问同一会话。用生命周期管理换取 1 ms，是净负收益——这与 #88「先量再做」的结论一致：没有数据显示需要优化。

**保留的收益**：既然构建是纯函数且逐字节稳定，`#90` 关心的「MCP 状态变化只影响结果不影响 schema」已经由 #137 保证（连接服务器后工具列表逐字节不变，见 `test_mcp`）。

结论：#138 关闭。若将来 `tools_build` 变重（例如引入动态工具发现），先把 16.8 µs 这个基线重测一次再决定。
