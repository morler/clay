## 现状

- 主代理硬上限 64 轮（`src/commands/context.h:464`），子代理 32 轮（`:465`）。
- 耗尽返回 `CLAY_RUN_OUT_OF_ROUNDS`（`src/providers/openai.c:909`、`openai_codex.c:1010`），`message.c:1650-1655` 把 turn 写成 `completed`，`message.c:1700-1705` 提示用户再发消息。
- 第 64 轮的工具结果没有被下一次请求消费；用户手动“继续”才会进入模型上下文。
- 子代理耗尽时部分 summary 会丢（#154 先修）。
- 主/子代理都通过 `clay_commands_run_completion` 调用 provider；OpenAI、Codex、Grok、Responses 的循环重复。

## 任务

1. 软/硬预算：
   - 段内软上限 48 轮；达到时在下一轮请求前注入一次可识别的收敛提示（检查剩余 todo、优先验证/收尾、不要扩展探索）。
   - 硬上限仍是 64 轮，作为安全网；不要在 provider 循环内部重置 round。
2. 调用方分段续跑（主/子代理各自实现，复用同一 helper）：
   - `rc == CLAY_RUN_OUT_OF_ROUNDS` 时，追加带固定标记的 synthetic user 消息（例如 `[clay:auto-continue]`），说明“从停下的地方继续，不重复已完成的调用；完成则给简短总结”。
   - 用同一 `messages`、同一 `ClayConversationStream`、同一组 callbacks 再跑一段；主代理最多 2 段，子代理最多 1 段（常量可调）。
   - 最后一段仍耗尽时，用 `tools=NULL, max_rounds=1` 做无工具收尾，消费最后一批工具结果并输出状态/未完成项。
   - 总预算：段数、总轮数、计费 token、墙钟时间任一达到即停；段边界检查 `should_abort`，取消返回 1。
3. synthetic 消息必须可识别，并让 `is_user_message`（`context.c:2076-2079`）与 `/compact` 的用户请求收集跳过它，避免污染“保留最近 6 个 user turn”的压缩窗口。
4. journal 语义：
   - 多段 turn 只记一次账、一个 turn；不要把第一段结束就标成最终 `completed`。
   - 增加可持久化的段数/是否续跑元数据，或在 turn state 中区分 `incomplete`；`/resume` 至少能看出“停在半路”。
   - 不实现完整 paused/checkpoint 恢复（后续独立 issue）。
5. provider 不改循环；Grok 继承 OpenAI、Responses 继承 Codex 的路径一并验证。

## 验收

- `tests/test_message.c` mock：第一次返回 2、第二次返回 0；断言只开一个 turn、synthetic 消息存在、最终输出/usage 不重复、取消在段边界生效。
- `tests/test_subagent.c`：子代理 32 轮耗尽后自动续跑一段并返回 summary；父代理结果正确。
- `tests/test_context_compact.c`：synthetic 消息不被当作真实 user turn，不改变保留窗口。
- `tests/test_request_log.c`：多段请求的 round 连续、条数正确、不重复记账。
- `make test-message test-subagent test-context-compact test-request-log` 通过；`make test` 通过。
- 手工：构造一个 64 轮 mock turn，确认不再停在“send another message”。

## 不做

- 不做 LLM 摘要交接/新上下文（等指标确认后独立 issue）。
- 不做 paused checkpoint/resume（后续独立 issue）。
- 不把 64 抬到 128。
- 不在 provider 内部自动续跑；保持 provider 层“每段最多 64/32”的清晰边界。
