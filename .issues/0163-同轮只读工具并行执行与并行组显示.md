## 现状

- provider 循环顺序执行 tool calls：src/providers/openai.c:706-746、src/providers/openai_codex.c:837-865；每个调用一次 on_tool_call/on_tool_result，UI 同时只有一个 spinner task（stream->tool_task）。
- 没有任何工具被标记为可并行；read/grep/glob/repo_map 与写工具走同一路径。
- 子代理内部已经并发调用这些工具（多个分支同时 read），所以 fs 工具本身在并发下可用；缺口在调度与可见性。
- neo：只读调用并发执行，组块 `● 3 tools in parallel` + 每调用一行，源顺序固定，状态行 `N tools in parallel`，失败行留在组内。

## 任务

1. 工具分类放在注册处：`ClayTool` 增加 `parallel_safe` 标志，`add_tool` 显式传入；read/grep/glob/repo_map 为 true，其余（write/edit/shell_exec/task_*/subagent/mcp/skill/ask_user/todowrite/memory_*/remember）为 false。不在 provider 里按名字硬编码。
2. 调度：同一 assistant 消息里有 ≥2 个 parallel_safe 调用时并发执行（上限 4，与 subagent 一致），其余调用按源顺序串行；结果按源顺序写回 messages；单个失败不影响其他调用。
3. 权限：read 的弹窗已在 `tool_lock` 上串行（src/commands/permissions.c:143），并发调用只在弹窗处排队；不得在持锁时等待其他并发调用。
4. UI：组开始前用 #160 的 live block 一次分配 N 行；header 显示 `N tools in parallel`，每行显示动词 + 目标（`Reading: path`、`Searching "pat"`）；结果只更新对应行的 glyph/detail/耗时，不重排。失败行保留在组内，错误正文按现有失败输出跟在组后。组结束 header 变 ✓/✗。below 状态行显示 `N tools in parallel`。
5. 取消：should_abort 传播到所有并发调用；已开始的返回取消结果，未开始的标记 cancelled；组块结算，不留活动行。
6. openai 与 codex 两条路径都覆盖（grok/responses 分别继承），调度逻辑抽成共享 helper，不复制。

## 验收

- `tests/test_message.c`：两个 read 并发（可控阻塞的 mock 工具验证时间重叠）、结果顺序、一失败一成功、取消结算。
- 同一并发组只产生一条 assistant tool_calls 消息和对应数量的 tool 消息；`tests/test_request_log.c` 请求条数不变。
- pty：3 调用组块行数稳定、header 从 ● 到 ✓、失败行保留。
- `make test-message test-pty test-openai-codex` 通过；`make test` 通过。
- 手工：一次读 3 个文件，墙钟明显短于串行。

## 不做

- 不并发写/编辑/shell（继续由 tool_lock 串行）。
- 不做跨 assistant 消息的流水线。
- 不并行 mcp 调用（server 可能非线程安全）。

## 规模

预计 20-30 轮；涉及 src/commands/message.c、context.h、src/providers/openai.c、openai_codex.c、src/render。
